# Runbook: billing go-live (live Razorpay, production)

Owner decision D-038 (2026-10-28): the platform reuses the **live Razorpay account** that the marketing site already uses for Future Builders payments. The keys are the ones in Vercel (`RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`). The platform API and worker read them from the production Key Vault, never from git, chat or a terminal history. `BILLING_ENABLED` stays `false` until launch.

> **These are LIVE keys. Every payment through them is real money from a real card or UPI account.** Nothing in steps 1–5 can charge anyone: the platform is dark and purchases are closed. Step 6 opens purchases.

Design: ADR-016 (billing), ADR-018 §2 (webhook through the web proxy). Code: `platform/api/src/billing/`. Infrastructure: `platform/infra/params/prod.bicepparam` (`var billingOn`), `platform/infra/main.bicep` (`razorpaySecrets`), `platform/infra/modules/containerApps.bicep` (`caj-soyl-billing-prod`), `platform/infra/modules/keyvault.bicep` (existence gate).

**Who does what:** 👤 = the owner (holds the Vercel and Razorpay dashboards and the Key Vault write role). 🛠 = the Lead (Bicep deploys and jobs). The Lead never sees a key or secret value.

## What gets wired

| Key Vault secret | Env var (api, worker, billing job) | Value comes from |
|---|---|---|
| `razorpay-key-id` | `RAZORPAY_KEY_ID` | Vercel `RAZORPAY_KEY_ID` (starts `rzp_live_`) |
| `razorpay-key-secret` | `RAZORPAY_KEY_SECRET` | Vercel `RAZORPAY_KEY_SECRET` |
| `razorpay-webhook-secret` | `RAZORPAY_WEBHOOK_SECRET` | **Generated by the owner** in step 2 (at least 16 characters). The same value goes into the Razorpay webhook at launch (step 6) |
| none (plain setting) | `RAZORPAY_PROVIDER=razorpay` | Bicep, only when `billingOn = true` |

The switch is **one line** in `platform/infra/params/prod.bicepparam`: `var billingOn = false`.

- `false` (now): no Razorpay env vars, no secret references and no billing job. The apps run with `RAZORPAY_PROVIDER=disabled`. A deploy needs none of the secrets.
- `true`: all of the above are added together. **Safe order is enforced:** the Key Vault module reads the three secrets' metadata through Azure Resource Manager (names only, never values). If any is missing, the deployment stops there with `ResourceNotFound`, and the Container Apps are left exactly as they were. (An app that references a missing Key Vault secret cannot start its new revision.) `validate.mjs` also fails if a Razorpay setting is ever given as a plain value, or if only some of the three are wired.

Names used below: resource group `rg-soyl-platform-prod`, Key Vault `kv-soyl-prod-tek7mx`, Log Analytics `log-soyl-prod`, billing job `caj-soyl-billing-prod`.

## 2. Put the three secrets into Key Vault 👤

Rules: never paste a value into a command line, chat, a file in the repo, or an email. Copy from Vercel to the clipboard and paste into a hidden prompt (CLI) or the portal field.

### CLI (values come from a hidden prompt, never from command history or arguments)

```bash
# kvset <secret-name>: reads the value without echo, writes it to a private temp file for az, deletes the file.
kvset() {
  local v f rc
  IFS= read -rs -p "Paste the value for $1 (hidden), then Enter: " v; echo
  [ ${#v} -ge 10 ] || { echo "too short or empty: $1 not set"; return 1; }
  f=$(mktemp); chmod 600 "$f"; printf '%s' "$v" > "$f"; unset v
  az keyvault secret set --vault-name "$KV" -n "$1" --file "$(cygpath -w "$f")" --encoding utf-8 -o none; rc=$?
  rm -f "$f"; [ $rc -eq 0 ] && echo "$1: set" || echo "$1: FAILED"; return $rc
}

# 1. Vercel → project → Settings → Environment Variables → RAZORPAY_KEY_ID (Production) → reveal (eye icon) → copy
kvset razorpay-key-id
# 2. Same for RAZORPAY_KEY_SECRET
kvset razorpay-key-secret
printf '' | clip          # clear the clipboard (and Win+V → Clear all, if clipboard history is on)
```

**The webhook secret.** Generate it yourself. It goes straight into Key Vault and into your clipboard, so you can save it in your password manager. You will paste it into the Razorpay webhook at launch (step 6).

## 4. Sync the plans: dry run, then for real 🛠

The Key Vault and the database are private, so `sync-plans` runs **inside Azure** as the job `caj-soyl-billing-prod`: the migrations image runs `migrate-entrypoint.mjs billing …` with the **worker** identity, which reads the Razorpay secrets and is `soyl_app` in the database. The job's built-in arguments are the **dry run**, which writes nothing to the database or Razorpay.

```bash
wait_job() {  # wait_job <execution name>
  until s=$(az containerapp job execution show -g $RG -n caj-soyl-billing-prod --job-execution-name "$1" --query properties.status -o tsv); \
        [ "$s" = Succeeded ] || [ "$s" = Failed ]; do echo "$s"; sleep 10; done; echo "billing job $1: $s"; }
job_logs() {  # console output of the job in the last 30 minutes (Log Analytics lags 2-5 minutes)
  az monitor log-analytics query -w "$(az monitor log-analytics workspace show -g $RG -n log-soyl-prod --query customerId -o tsv)" \
    --analytics-query "ContainerAppConsoleLogs | where TimeGenerated > ago(30m) | where ContainerJobName == 'caj-soyl-billing-prod' or ContainerAppName == 'caj-soyl-billing-prod' | project TimeGenerated, Log | order by TimeGenerated asc" -o table; }

# 4a. Dry run (the job's default arguments)
EXEC=$(az containerapp job start -g $RG -n caj-soyl-billing-prod --query name -o tsv); wait_job $EXEC; job_logs
```

Expected dry-run output, one JSON line each:
- `{"level":"info","msg":"billing job","appEnv":"prod","provider":"razorpay","keyMode":"live","command":"sync-plans"}`. If `keyMode` is not `live`, stop: the key in Key Vault is not the live key.
- Up to four `db_insert` lines (`free`, `plus`, `pro`, `board_exam_pass`), unless the plan rows already exist.
- Four `razorpay_create` lines: Plus monthly 19900 paise, Plus yearly 149900, Pro monthly 29900, Pro yearly 249900. A `razorpay_link` line instead means a matching plan already exists and is reused.
- `{"summary":true,"dryRun":true,"razorpay":"synced","changes":N,"message":"changes pending (dry run)"}`, and the execution ends `Succeeded`.

A Razorpay error here (for example HTTP 401, or a message that Subscriptions are not enabled) means the keys or the account are not ready. Fix that first; the dry run changed nothing.

```bash
# 4b. For real (same image, arguments overridden for this one execution)
EXEC=$(az containerapp job start -g $RG -n caj-soyl-billing-prod --image "$SOYL_MIGRATE_IMAGE" --container-name billing \
         --args "/app/migrate-entrypoint.mjs" "billing" "sync-plans" --query name -o tsv); wait_job $EXEC; job_logs

# 4c. Idempotency check: the dry run again must say "no changes"
EXEC=$(az containerapp job start -g $RG -n caj-soyl-billing-prod --query name -o tsv); wait_job $EXEC; job_logs
```

`sync-plans` is idempotent. It matches Razorpay plans by our notes (`app=soyl-academy`, plan, interval), amount, currency and period, so re-running creates nothing. Plans go into the live account next to the Future Builders data. They are named "SOYL Academy Plus (monthly)" and so on, and do not affect Future Builders orders.

### 6a. Register the webhook (OA-21) 👤

The route: Razorpay POSTs to `https://www.soylai.com/api/platform/v1/webhooks/razorpay`. The web proxy (`app/(platform)/api/platform/[...path]/route.ts`, ADR-018 §2) forwards it to the API route `POST /v1/webhooks/razorpay`. The body is streamed through byte for byte (never parsed or re-serialised), and only on this path the `X-Razorpay-Signature` and `X-Razorpay-Event-Id` headers are passed on. The API checks the HMAC over the raw bytes; an e2e test changes one byte and gets 400.

Razorpay dashboard (live mode) → **Account & Settings → Webhooks** → **+ Add New Webhook**:

- **Webhook URL:** `https://www.soylai.com/api/platform/v1/webhooks/razorpay`. Use exactly this URL with `www`. Never use soylacademy.com: SOYL does not own that domain.
- **Secret:** the webhook secret from your password manager (step 2). Razorpay does not show it again; Key Vault keeps the copy the API uses.
- **Alert email:** your ops inbox (optional).
- **Active events.** Tick exactly these 17, which are `HANDLED_EVENTS` in `platform/api/src/billing/webhooks.ts`:
  - `subscription.authenticated`, `subscription.activated`, `subscription.charged`, `subscription.pending`, `subscription.halted`, `subscription.cancelled`, `subscription.completed`, `subscription.updated`, `subscription.paused`, `subscription.resumed`
  - `payment.authorized`, `payment.captured`, `payment.failed`
  - `order.paid`
  - `refund.created`, `refund.processed`, `refund.failed`
- **Create Webhook.**

The same account also sends Future Builders payments (`payment.captured`, `order.paid`) to this webhook. The platform records them and answers 200 with outcome `ignored` (`not_ours`): it looks up only its own orders and subscriptions, so nothing changes. The marketing site has no webhook of its own; it only creates orders.

## 7. Roll back

| Situation | Action |
|---|---|
| Stop **new** purchases at once | Set `BILLING_ENABLED: 'false'` in prod.bicepparam and redeploy (3c). Emergency (reconcile with Bicep afterwards): `az containerapp update -g $RG -n ca-soyl-api-prod --set-env-vars BILLING_ENABLED=false -o none`. Webhooks, renewals, cancellations and reconciliation keep working by design: existing subscribers are unaffected. |
| A bad migrations image in the billing job | Re-run the job with the previous digest (`--image <previous soyl-migrate@sha256:…>`), then redeploy Bicep with it. |
| The webhook misbehaves | Razorpay dashboard → Webhooks → edit → untick **Active**. Razorpay keeps the failed events; after the fix, re-enable it and run `reconcile --dry-run`, then `reconcile` with the billing job (razorpay-webhook-replay.md). |
| Unwire billing entirely (only with no paying subscribers, or to cut off the keys) | Set `var billingOn = false` and redeploy. The apps drop `RAZORPAY_*` (provider `disabled`); webhooks then answer 404 `not_configured` and the nightly reconcile is skipped. An incremental deployment does **not** delete the job: `az containerapp job delete -g $RG -n caj-soyl-billing-prod --yes` (it is manual-trigger only and harmless if kept). The Key Vault secrets stay unless the owner deletes them; the vault has purge protection, so deleted secrets are recoverable for 90 days. |
| Keys leaked or suspected | 👤 Razorpay → API Keys → **Regenerate**. Put the new values into Vercel (redeploy the marketing site) **and** Key Vault (steps 1–2) at the same time. 🛠 `az containerapp revision restart` for the api and the worker, so they read the new version. The billing job reads the latest version on its next run. |
| Webhook secret leaked | 👤 Generate a new one (step 2). Set it in Key Vault first, the Lead restarts the API revision, then update it on the Razorpay webhook. Deliveries in the gap fail and Razorpay retries them. If any are lost, the nightly reconcile repairs the state. A zero-gap rotation needs the `razorpay-webhook-secret-previous` slot (`RAZORPAY_WEBHOOK_SECRET_PREVIOUS`), which is not wired yet (see the handoff's follow-ups). |
